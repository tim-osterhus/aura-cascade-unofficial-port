# Aura Cascade Reimagined: NeoForge 1.21.1 Port Plan

Date: 2026-09-28

Status: planning complete; implementation not started. This document does not
claim a compiling NeoForge build, passing NeoForge gameplay, or publication.

## 1. Outcome And Scope

Release Aura Cascade Reimagined **0.2.2 beta for Minecraft 1.21.1 NeoForge** on
the existing CurseForge project. Begin platform work from committed Fabric
0.2.1 while the separate Mod Playtesting workflow finishes its inventory and
canonical 0.2.2 repairs. Incorporate the accepted repair set before release.

- Retain mod ID `aura`, registry IDs, attribution, license, progression, and
  existing approved modernizations.
- Preserve the amethyst shard plus eight gold nuggets recipe yielding two
  White Aura Crystals. Keep guide text immersive, without recipe-history copy.
- Retain the navigable Patchouli encyclopedia, physical accessory slots, and
  all five 0.2.1 feedback/discoverability fixes.
- Implement native NeoForge integration, not a Fabric compatibility-layer pack.
- Do not combine this with a Minecraft version upgrade, new gameplay, Curios
  support, or an Architectury/shared-source refactor.
- Fabric remains the canonical gameplay implementation. NeoForge-specific
  behavior must be a necessary platform adaptation, not an undocumented fork.
- Cross-loader multiplayer and automatic Fabric-world conversion are not
  promised. Native NeoForge save/reload support is required.

## 3. Source Inventory And Design Decisions

At `44cc057`, 20 of 138 main Java files directly reference Fabric; the external
energy adapter also references Team Reborn Energy. The mixin configuration has
12 mixin/accessor entries. These counts describe integration points, not the
percentage of work remaining.

| Area | Existing source anchors under `src/main/java/pixlepix/auracascade/` | Target work |
| --- | --- | --- |
| Bootstrap and configuration | `AuraCascadeMod`, `config/AuraConfig` | Native mod entrypoint and config-path lookup; retain current config format/defaults unless technically necessary to change |
| Registration | `block/AuraContent`, `item/AuraItems`, `item/AuraDiscoverability` | Register blocks, items, entities, block entities, menus and creative tab at the correct NeoForge lifecycle stages; inspect all registration calls, not just Fabric imports |
| Player state | `compat/AuraAccessoryInventory` | Persistent NeoForge attachment, explicit owner-only synchronization, exact death/clone semantics |
| Packets and menus | `compat/AuraAccessoryNetworking`, `network/BookshelfCoordinatorNetworking`, client networking and screens | Native payload registration and sending; preserve server authorization and vanilla codecs where usable |
| Gameplay hooks | `item/AuraItems`, `item/PrismaticWandItem`, `block/entity/KaleidoscopicEnchanterLogic`, `enchantment/KaleidoscopicOriginalEffects` | Map interaction, attack, break, death and tick callbacks while preserving side, phase, cancellation and ordering |
| Fairy lifecycle | `fairy/FairySystem` | Entity load, logout, server stop, respawn and dimension-change hooks; avoid duplicate fairies or dropped state |
| Client integration | `client/AuraCascadeClient`, `client/AuraFairyClientRegistry`, `compat/client/AuraAccessoryClient`, client renderers | HUD, keys, menus, screens, creative-tab behavior, entity/block-entity render registration; isolate client class loading |
| External energy | `compat/AuraFluxEnergyBridge`, `AuraFluxBridge`, `AuraFluxTransferLogic` | Replace Fabric transaction/storage calls with native NeoForge energy capability integration while retaining gameplay conversion rules |
| Mixins | `src/main/resources/aura.mixins.json`, `mixin/` | Review all 12 entries against patched target classes; retain a mixin when it remains the simplest faithful hook |
| Resources and tests | `src/main/resources/`, `src/test/java/` | Reuse content and logic tests; replace loader metadata and loader-specific assertions without weakening behavior coverage |

Use the official 1.21.1 ModDevGradle MDK as the build reference, not as a reason
to overwrite source layout. Pin exact NeoForge 21.1.x, ModDevGradle, Gradle,
and Patchouli versions after resolving and testing a compatible set. No dynamic
versions. Java 21 and the 1.21.1 target are documented upstream. [S1, S2]

Patchouli `1.21.1-93-NEOFORGE` is available from the original Patchouli project
306770. Verify Maven resolution and runtime loading before locking it. Do not
reuse the Fabric Edition project/file dependency from the 1.21.11 port. [S6]

NeoForge 1.21.1 attachments require explicit client synchronization. Their
death-copy and clone handling must distinguish death from returning from the
End. Translate the existing inventory contract, rather than enabling copy and
drop paths independently and risking duplication. [S3]

Register payloads through NeoForge's payload event/registrar and send only to
the appropriate side and recipient. Retain reusable vanilla payload/stream
codec definitions, check thread context, and preserve server-side validation.
Do not grant authority based on client-supplied inventory state. [S4]

For energy, target the **1.21.1 `IEnergyStorage` / block energy capability**,
not the newer `EnergyHandler` API from later NeoForge documentation. [S5]
Simulation is not a rollback transaction. Probe acceptance without mutation,
account for actual accepted energy on insertion, preserve bounded integer
conversion, and never charge Aura for rejected energy. Retain connected-machine
limits and sided lookup behavior. Do not invent a generic transaction framework.

## 4. Milestones And Exit Criteria

### N0: Isolation And Baseline

Can begin while the canonical audit is running.

1. Establish the isolated worktree/branch and copy this spec into it.
2. Record source commit, released JAR hash, dependency manifest and branch owner.
3. Reproduce the canonical unit/build baseline in that checkout before replacing
   the build; compare against the recorded 252 tests in 62 suites. Explain any
   discrepancy instead of treating the historical count as a new test result.
4. Inventory loader-bound code, metadata, tests and launch scripts. Record
   baseline known defects; do not repair them as part of the port scaffold.
5. Create a target audit record and a target forward-port ledger. Keep the
   existing 1.21.11 ledger untouched.

Exit: isolated baseline and explicit scope; no changes to the audit environment.

### N1: Native Build And Registration

Can begin immediately after N0; no dependence on final 0.2.2 fixes.

1. Replace Loom/Fabric dependency configuration with pinned native NeoForge
   build configuration and development client/server runs.
2. Add `META-INF/neoforge.mods.toml`, dependency declarations and mixin wiring;
   remove Fabric production metadata and bundled Team Reborn Energy once replaced.
3. Port common/client bootstrap, registries, config path, and creative inventory
   registration. Adapt remaining call sites sufficiently for a complete compile.
4. Keep registry IDs, resource paths and content unchanged. Validate registry
   initialization order, including static references and menu/entity suppliers.
5. Configure a loader-distinct output name, proposed
   `aura-cascade-neoforge-0.2.2+1.21.1.jar`; use distinct prerelease candidate
   identities and hashes during development, not overwritten release artifacts.
6. Resolve Patchouli and confirm required dependency failure messages are clear.

Exit: a complete compile/build and clean client/dedicated-server bootstrap with
correctly registered content. No feature removal or no-op stubs to pass the gate.
N2 implementation can overlap late N1, but bootstrap alone is not gameplay proof.

### N2: Loader Behavior And Target Test Tools

Can proceed while the canonical audit/patch work continues.

1. Port interaction/lifecycle hooks and document each old callback's target
   hook, logical side, tick phase, ordering and cancellation behavior.
2. Implement accessories, owner-only sync, menu packets and bookshelf requests.
   Preserve all slot constraints and server-side distance/menu/access checks.
3. Review all mixins against NeoForge-patched sources and verify production
   application. Do not run an equivalent event and mixin effect twice. Do not
   silence failed injections by loosening required-match checks indiscriminately.
4. Port HUD, keybindings, render registration, screens and creative-tab retention.
5. Implement native Flux energy support and focused rejection/partial-acceptance,
   sided-receiver, receiver-limit and conservation tests.
6. Adapt loader-coupled regression/bootstrap tests. Track replaced assertions;
   do not delete tests merely because they expose a migration problem.
7. Adapt packaged-client/server launch and memory measurement for NeoForge.
   Existing `scripts/qa/observer` and `scripts/qa/multiplayer` helpers declare
   Fabric metadata: they cannot be presumed to run unchanged on NeoForge.
8. Prefer small separate NeoForge QA helpers or suitable existing Mod Lab
   facilities. Keep the helper artifacts out of the production JAR and release
   dependencies. Do not turn a mod port into a general QA-framework rewrite.

Exit: automated regressions pass; packaged native client/server and bounded
multiplayer checks run against a hash-identified candidate; no required gameplay
feature remains a stub. Record inherited canonical defects separately from
target regressions. Early checks will be rerun after canonical repair integration.

### N3: Canonical 0.2.2 Repair Integration

Can start incrementally as reviewed fixes arrive; final exit depends on the
other workflow's completed triage and frozen canonical source checkpoint.

1. Obtain a handoff per fix: defect ID, canonical commit, affected behavior,
   regression tests, fixture/oracle, live evidence, and remaining limitations.
2. Import coherent commits with `git cherry-pick -x` when practical. For a
   heavily loader-bound change, adapt explicitly and record its source commit.
   Do not merge an entire Fabric branch into the target.
3. Keep target adaptations in distinct commits; resolve conflicts by behavior,
   not by choosing all of one side. Run affected tests immediately.
4. Maintain the ledger: defect ID -> canonical SHA -> target SHA -> tests ->
   packaged candidate hash -> acceptance status, including justified non-applicable
   or deferred items. Never silently omit a fix.
5. Freeze the accepted Fabric 0.2.2 source and repair scope. Compare gameplay
   code, recipes, tags and guide resources against it, explaining target deltas.

Current handoff candidates, not the final backlog:

| ID | Current record | Required target acceptance |
| --- | --- | --- |
| AC-022-001 | Breeder accepts juveniles | Valid adult pair works; juvenile, cooldown, species and ring-off controls do not |
| AC-022-002 | Duplicate offspring observed; causal explanation still under investigation | Repeated adult-pair trials produce one child/event, respect cooldown, and match a vanilla-fed control |
| AC-022-003 | Binding Ring costs link opens wrong entry | Correct costs destination and Back navigation at tested GUI scales |

Unloaded-receiver and Orange-restart observations need validated preconditions
and independent triage. An assertion failure is not automatically a product
defect. Do not change canonical rules solely to satisfy an invalid fixture.

Exit: complete reconciliation against the frozen canonical 0.2.2 scope,
including every accepted repair and its target disposition. Publication of the
Fabric artifact is not itself a prerequisite if its source and acceptance are
settled; a moving/unreviewed repair backlog is a prerequisite failure.

### N4: Final NeoForge Acceptance

Early tests can run during N2/N3; final sign-off must follow N3 on the release
candidate. Use the production JAR in a clean installation, not only Gradle runs.

| Gate | Required evidence |
| --- | --- |
| Build and packaging | Unit/resource tests, production build, license, correct loader/game/dependencies, no Fabric runtime or test helpers bundled |
| Install and side safety | Clean client plus dedicated server; recipes/tags/registries load; no missing textures or common-side client class crashes |
| 0.2.1 visual fixes | Actual dropped-item reaction animation, empty-node placement flow preview, complete creative tab, stable HUD without update gaps, clearly separated guide links |
| Guide and acquisition | Click navigation/Back, recipe rendering, repaired Binding link, amethyst recipe, readable pages at representative GUI scales; separate layout automation from manual coverage |
| Networks and machines | Natural/mixed/Orange flow, pump triggers, redstone controls, power accounting, consumers, vortex and ritual progress with valid positive/negative controls |
| Gear and hooks | Representative mining/combat/enchantment combinations, damage/explosion protection, Forbidden Fruit completion/cancel, portable-hole and item lifetime behavior |
| Storage and authority | Bookshelf search/retrieval, book capacity/filters, item conservation, inaccessible menu/invalid request rejection |
| Player lifecycle | Two clients; owner-only state; equip/remove/bind; death with keepInventory on/off; respawn, End return, dimension change, logout/reconnect and full server restart; no item/fairy duplication |
| Native persistence | Disk round trips for aura, books/shelves, accessory state, fairies, vortex receipts and ritual queues; distinguish serialized state from legitimate post-load ticking |
| External energy | Controlled receiver fixture plus at least one real compatible NeoForge energy receiver; full/rejecting/partial/sided receivers, disconnect/reconnect and over-limit network; actual accepted energy matches Aura charge |
| 0.2.2 fixes | Rerun every applicable repaired defect on the NeoForge candidate, including negative controls |
| Resource envelope | Measured build and packaged-runtime process trees; heap, private allocation and working set reported separately |

Carry over the canonical inventory's test specifications and expected behavior,
not its PASS labels. Mark every obligation as target-pass, target-fail, inherited
evidence only, untested, or justified not-applicable. Tests of unchanged pure
logic remain useful but do not demonstrate loader event behavior.

Use ordinary actions for player-facing claims. Fixtures may supply materials
or establish preconditions, but must not inject the outcome being tested. Record
candidate hash, environment, preconditions, action sequence, expected/observed
results and evidence. Independent review should reproduce high-risk cases.
Disclose all remaining coverage gaps; do not claim exhaustive modpack testing.

Exit: no unresolved release-blocking target regression, loss/duplication issue,
or required 0.2.2 repair; all required gates have candidate-specific evidence.
Unexpected gaps require an explicit disposition, not an automatic green status.

### N5: Release And Publication

Wait for N3 and N4. This is a NeoForge 0.2.2 release, not a relabeled 0.2.1 JAR.

1. Review and push the validated target commits using the requested identity;
   record source SHA, build environment, dependency versions and artifact hash.
2. Prepare NeoForge-specific installation notes, 0.2.2 changes, known limits,
   test scope and release manifest. Preserve attribution and license.
3. Adapt/test existing publishing helpers for a NeoForge loader selection and
   Minecraft 1.21.1. Do not reuse a hardcoded Fabric release payload.
4. Upload beta to the existing Aura Cascade Reimagined project, with the correct
   Patchouli dependency and a loader-distinct filename/display name. Never put
   a NeoForge JAR behind a Fabric label or replace historical artifacts.
5. Verify the returned file ID and selected dependencies/game/loader. Record
   upload acceptance separately from moderation/public download availability.
   Avoid duplicate uploads when checking an uncertain response.
6. Close the target ledger and stop owned test processes; preserve evidence.

## 5. Parallel Work And Dependency Boundary

| Work | While inventory runs | While canonical patches land | Must wait for frozen 0.2.2 |
| --- | --- | --- | --- |
| Isolated checkout, toolchain and dependency pinning | Yes | Yes | No |
| Registrations, client integration, metadata and packaging | Yes | Yes | No |
| Networking, attachments, lifecycle and energy adapters | Yes | Yes, watch overlapping fixes | No |
| NeoForge QA helper/launcher adaptation | Yes | Yes | No |
| Early target regressions and packaged gameplay | Yes, preserve inherited failures | Yes, rerun affected checks | Final sign-off only |
| Import accepted gameplay repairs | As reviewed commits become available | Yes, incremental | Complete reconciliation |
| Final artifact, complete repair acceptance and publication | No | Preparation only | Yes |

The useful parallel milestone is a working, independently exercised native
NeoForge build ready to receive the final repairs. Most platform implementation
does not need to wait. The final gameplay contents and release approval do.
This is a dependency statement, not an estimate that most total effort is done.

## 6. Execution Lanes

Use a small number of bounded lanes, mostly the user's preferred Luna Max
workers, rather than one agent per file. These are proposed assignments; no
agents were launched for this planning task.

- Integrator: toolchain/entrypoint ownership, contracts, canonical-fix ledger,
  cross-lane review and release decision.
- Luna implementation lane: bounded registration/client/resource changes and
  focused tests after the integrator establishes the target scaffold.
- Luna QA/tooling lane: loader-specific packaging/observer adaptation, resource
  coverage, test preservation and independent artifact review.
- Sol specialist lane: attachment/network lifecycle, event-order conflicts and
  non-transactional energy accounting where needed, with bounded deliverables.
- Astra low-effort playtesting lane, subject to available model settings:
  independent in-game/visual acceptance once the candidate and tools are usable.

Assign disjoint files or isolated agent worktrees. Shared bootstrap/registry
integration stays with one owner. Each handoff includes exact files, source
checkpoint, tests actually run, unresolved failures and evidence. Do not spend
multiple lanes independently rediscovering the same loader API changes.

## 7. Runtime Isolation And Memory

The user permits concurrent playtesting sessions; there is no global single-game
lease. That does not permit sharing writable worlds, replacing another lane's
JAR, or controlling its client window. Use distinct run directories, world
copies, ports, logs and process ownership records. Never kill processes by a
broad `java` name match or run a shared `gradle --stop` against another lane.

Retain a conservative 4.5 GB own Minecraft/build workload target until measured;
Codex/ChatGPT desktop is excluded. Record the byte/unit interpretation explicitly.
Use one Gradle worker, bounded heaps, no persistent daemon and a single test
fork initially. Build and test serially within this lane when necessary to fit
the budget; other lanes need not wait merely because this one is running.

Measure first-time NeoForge setup as well as warm builds, and the combined
owned client/server workload. Report resident working set and private allocation
separately. JVM heap caps and sampled monitors are not hard process RAM limits.
If the selected toolchain or multiplayer profile cannot meet the budget, record
the observed blocker and revise scheduling/settings before claiming compliance.

## 8. Risks And Decisions To Close During Implementation

- Dependency pinning: exact build-plugin/Gradle/NeoForge combination is not yet
  resolved. N1 must prove resolution, compile, and packaged loading.
- Event/mixin semantics: the same Minecraft version does not imply identical
  patched methods or event order. Inspect target sources and test interactions.
- Energy: preserve numerical rules without assuming simulation can undo real
  insertions. Test partial acceptance and integer limits explicitly.
- Persistence: shared registry IDs alone do not establish Fabric attachment
  storage compatibility. Test copied-world migration only as a separate optional
  study; document it as unsupported/unverified unless accepted evidence exists.
  Do not open a user's only save in the alternate loader.
- Audit churn: valid new defects can expand N3/N4. Keep the target moving on
  platform work, but do not declare 0.2.2 complete against an obsolete backlog.
- QA infrastructure: Fabric helpers need adaptation. A helper failure is not a
  gameplay failure; preserve the distinction and provide alternate observation.
- Maintenance: transfer future canonical patches as small tracked commits. Only
  consider shared-source extraction later if actual repeated conflict justifies it.
