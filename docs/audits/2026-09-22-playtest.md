## Results

### Aura guide item does not open the reader

Observed failure. In the disposable world:

1. Run `/give @s aura:encyclopedia_aura` and select hotbar slot 1.
2. Right-click in air twice, checking the actual game image after each use.
3. No book screen opens. `/data get entity @s SelectedItem` shows generated
   written-book pages on `aura:encyclopedia_aura`, so use populated the content.
4. Give the vanilla control below, select slot 2, and right-click using the same
   targeted input helper. The vanilla reader opens with `Control page`.

```mcfunction
/give @s minecraft:written_book[written_book_content={title:"QA",author:"QA",pages:['{"text":"Control page"}']}]
```

Evidence: `17.37.45` (Aura item remains held, no reader) and `17.40.33`
(vanilla control reader). This distinguishes the observed Aura opening failure
from general inability to right-click. The exact-item check in vanilla book
opening is a source-level hypothesis supplied during triage, not independently
proven by these screenshots.

### Node outline and support-face rendering

Observed visual defects in the actual Aura block, not a substitute model.
The QA fixture placed stone at `9 180 8` and `aura:aura_node` at `9 181 8`.
From `12.5 180 11.5`, yaw 135, pitch 0, the small cube has a full-block selection
outline. The supporting stone top face is absent in the exposed area around
the small cube. From `/tp @s 11.5 182 10.5 135 40`, the missing top surface and
view through the support are clearer.

Evidence: 17.48.07 and 17.48.30. Camera settled downward after teleport because
the player was not flying; the listed second pose describes the captured
teleport checkpoint, not a maintained flight pose.

The parent's code hypothesis was a small model with default full-block shapes
and occlusion. The screenshots demonstrate outline/face mismatch; collision
volume was **not** separately tested. No comprehensive particle/charge-feedback
or empty-hand node interaction test was performed.

### Pump, network, and smelter comparison

Actual integrated-server behavior, with command-built QA fixtures. These are
not survival acquisition tests. The parent-authored datapack is under the
disposable save's `datapacks/aura_audit/data/aura_audit/function` directory.

After `/reload`, run `/function aura_audit:smelter_setup`. It seeds 20,000 red
aura in a creative pump at `8 182 8`, places upper nodes at `8 188 8` and
`9 188 8`, and a lower node at `9 181 8`. After five running-world seconds it
adds the adjacent smelter and raw iron, then checks ten seconds later.
No stored power is injected.

Corrected run at 17:50:25:

- 17:50:30: upper red aura 12,456; lower stored power 0.
- 17:50:40: no iron ingot observed; lower power 0; smelter power/progress 0 / 0.
- Screenshot 17.50.47 preserves the failed checkpoint and raw input.

An earlier fixture had slash-separated scheduled function identifiers instead
of colons, so its scheduled checkpoints did not run. Parent corrected that QA
setup typo. A manual network check was also run before the corrected repeat.
These setup issues are not counted as mod defects.

For one comparison, run `/reload`, then `/function aura_audit:smelter_spaced`.
Upper nodes are `8 188 8` and `10 188 8`, with one air block between them; lower
node is `10 181 8` and smelter is `11 181 8`. The fixture seeds aura, not power,
and supplies raw iron.

- Started 17:55:39; checkpoint 17:55:49 reports **iron ingot produced**.
- Upper red aura 2,145; lower red aura 11,684.
- Smelter power/progress 29,007 / 1.
- Screenshot 17.56.09 visibly shows the output ingot above the smelter.

Thus the spaced circuit passes the bounded pump-to-smelter scenario, while
the adjacent configuration stalls. Mutual redstone disabling is a source-level
hypothesis supplied by the parent; this test does not independently isolate
that mechanism or establish intended adjacent-node behavior. Direct smelter
power bypass was unnecessary and was not performed.
